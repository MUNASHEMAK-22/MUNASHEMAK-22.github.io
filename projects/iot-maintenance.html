How the detection works

Each machine establishes its own 14-day operating baseline (mean and standard deviation for temperature and vibration). Every new reading is scored against that baseline using a z-score:

temp_z = (reading.temperature - baseline_mean) / baseline_stddev
vibr_z = (reading.vibration - baseline_mean) / baseline_stddev

is_anomaly = temp_z > 2.5 or vibr_z > 2.5

A single noisy reading isn't enough to trigger an alert — that would flood the dashboard with false positives from ordinary sensor noise. The alert only fires once 3 consecutive hourly readings exceed the threshold, which is what separates a genuine drift pattern from a one-off spike:

if is_anomaly:
    consecutive_anomalies += 1
else:
    consecutive_anomalies = 0

is_sustained_anomaly = consecutive_anomalies >= 3

On both machines that failed, the model flagged a sustained anomaly roughly 9 days before the failure event — enough lead time to schedule maintenance during a planned window instead of reacting to unplanned downtime. Just as importantly, the four healthy machines produced zero false alerts across 90 days of hourly monitoring, which matters as much as catching the real failures: a system that cries wolf gets ignored.

What I'd build next

  • Replace the fixed z-score threshold with a model that adapts per machine type, since baseline "normal" varies by equipment class.
  • Add a maintenance-cost estimate to each alert, translating lead time into a projected downtime-avoided figure.
  • Stream readings in near-real-time instead of batch-processing a static CSV export.
