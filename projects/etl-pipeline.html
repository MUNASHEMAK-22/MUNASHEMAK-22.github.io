Automated ETL Pipeline for Business Reporting

A messy raw sales export, full of duplicates and inconsistent formatting, turned into a validated SQL database that powers a live Power BI dashboard — with no manual cleanup.

The problem

Sales data lands as a raw CSV export from an order system, and it looks exactly like real-world exports do: dates in three different formats, region names inconsistently capitalized, prices sometimes with a currency symbol and sometimes without, missing sales-rep values, and a small percentage of accidentally duplicated rows from the export process itself.

None of it is usable for reporting until someone, or something, cleans it. Doing that by hand every reporting cycle doesn't scale and introduces its own errors. The goal was to remove that manual step entirely.

What the raw data actually looked like

A representative sample, unedited, straight from the source export:

04-13-2025 East Noise Cancelling Headphones$149.994T. Nguyen

Three date formats in the same column, inconsistent region casing and stray whitespace, a mixed currency format, and blank sales-rep fields — all in a 1,084-row file. This is what the pipeline had to handle without hardcoding fixes for one file.

The pipeline

A single Python script runs the full extract-transform-load process end to end and can be re-run on any new export without modification.

1. Extract

Reads the raw CSV into memory as structured rows.

def extract(path: Path) -> list[dict]:
    with open(path, newline="") as f:
        rows = list(csv.DictReader(f))
    log.info("Extracted %d raw rows from %s", len(rows), path.name)
    return rows

2. Transform

This is where the real work happens: normalizing three date formats to ISO 8601, stripping currency symbols, standardizing region casing, filling missing sales reps, and deduplicating exact-match rows.

def parse_date(raw: str) -> str:
    for fmt in ["%Y-%m-%d", "%d/%m/%Y", "%m-%d-%Y"]:
        try:
            return datetime.strptime(raw.strip(), fmt).strftime("%Y-%m-%d")
        except ValueError:
            continue
    raise ValueError(f"Unrecognized date format: {raw}")

def clean_price(raw: str) -> float:
    return float(raw.replace("$", "").strip())

Every row that fails validation is logged and dropped rather than silently corrupting the dataset — a pipeline that fails loudly is more trustworthy than one that fails quietly.

3. Load

Clean rows are loaded into a SQLite database with an idempotent reload, so re-running the pipeline on a refreshed export never creates duplicate data.

cur.execute("DELETE FROM sales")  # idempotent reload
cur.executemany("""
    INSERT INTO sales (order_date, region, product, unit_price,
                        quantity, revenue, sales_rep)
    VALUES (:order_date, :region, :product, :unit_price,
            :quantity, :revenue, :sales_rep)
""", rows)

4. Visualize

Power BI connects directly to the SQLite database, so refreshing the dashboard is just re-running one script — no manual export-clean-import cycle.

Because the pipeline output is already clean, the downstream dashboard could ask harder questions immediately — for example, it surfaced a 44% revenue drop in the West region between Q2 and Q3 within the underlying dataset, entirely from the pipeline output, with no manual data wrangling in between.

What I'd build next

  • Schedule the script to run automatically (cron or a lightweight cloud function) instead of a manual trigger.
  • Move from SQLite to a cloud-hosted database (e.g. Postgres on Supabase) so the dashboard can refresh from anywhere.
  • Add automated data-quality tests so a malformed future export fails the pipeline with a clear error instead of loading bad data.
